# 문제 가설 정의 가이드

## 목적

고객 여정 분석과 고객 경험 조사 데이터를 기반으로 핵심 문제 가설과 근본원인을 도출하고,
문제검증 인터뷰를 통해 문제가설을 검증함. 그리고 비즈니스 가치를 도출함.

## 방법론

### 1. 문제 가설과 근본원인 도출

가장 큰 현상문제 3개를 도출하고 5WHY로 근본원인 도출함.

#### 5WHY 진행 방식 (발산-수렴-선택)

5WHY는 한 명이 혼자 작성하지 않고, 팀원 각자가 따로 발산한 뒤 수렴하여 선택하는 3단계로 진행함.

| 단계 | 수행자 | 수행 내용 | 결과 |
|------|--------|----------|------|
| **발산** | product-owner, service-planner, domain-expert, architect, ai-engineer (병렬) | 서로의 결과를 보지 않고 각자 전문 관점에서 5WHY 사슬을 따로 작성 | 팀원별 5WHY 사슬 |
| **수렴** | service-planner | 팀원별 사슬을 취합하여 유사한 고리와 근본원인을 묶고, 줄기가 갈리는 지점과 출처 팀원을 표기 | 수렴된 5WHY 후보 |
| **선택** | product-owner | 수렴된 후보 중 줄기와 근본원인을 선정하여 확정 | 확정된 5WHY와 근본원인 |

- 발산 단계는 팀원 수만큼 동시에 수행하고, 한 팀원의 결과를 다른 팀원에게 미리 전달하지 않음
- 사용자가 현상문제나 5WHY 원안을 직접 제시한 경우에도 같은 3단계로 진행함
- 수렴·선택 결과에는 어느 팀원의 사슬에서 나온 고리인지 출처를 남김

#### 5WHY 작성 형식

| 단계 | 질문 및 응답 |
|:----:|-------------|
| **WHY1** | 왜 {현상}인가? → {응답} |
| **WHY2** | 왜 {WHY1 응답}인가? → {응답} |
| **WHY3** | 왜 {WHY2 응답}인가? → {응답} |
| **WHY4** | 왜 {WHY3 응답}인가? → {응답} |
| **WHY5** | 왜 {WHY4 응답}인가? → {응답} |

- WHY1은 현상문제에 대한 질문 + 질문에 대한 응답으로 작성
- WHY2~WHY5는 이전 WHY의 응답에 대한 질문 + 질문에 대한 응답으로 작성
- 한 답에는 원인 하나만 둠. 서로 독립적인 원인을 한 칸에 섞지 않음
  (하나의 원인이 여러 측면에 관련되는 것은 허용)
- 원인과 그 결과를 한 칸에 함께 쓰지 않음. 다음 질문이 결과만 받아 원인 고리가 끊기는 것을 막기 위함
- 사람 본성·장르 성질처럼 바꿀 수 없는 사실에 닿으면 바닥임을 밝히고 그 앞 칸에서 멈춤

#### 다층적 근본원인 검토

아래 4가지 측면은 원인 후보를 빠뜨리지 않도록 살펴보는 출발점이며, 검토 범위를 제한하지 않음.
범주 밖의 원인도 검토하고, 하나의 원인이 여러 측면에 걸쳐 있어도 허용함.

| 측면 | 검토 항목 |
|------|----------|
| **사용자 심리적** | 인지 부하, 감정, 동기, 습관, 저항감 |
| **제도/시스템적** | 정책/규정, 프로세스, 권한 구조, 인센티브, 예산/자원, 기존 시스템 제약 |
| **맥락적** | 조직 문화, 업계 관행, 시장 상황, 타이밍 |
| **커뮤니케이션** | 정보 전달, 교육, 피드백 체계 |

- 최종 선정 대상은 '측면'이 아니라 '현상을 설명하는 구체적인 원인'임. 원인을 범주에 맞추려고 표현을 바꾸거나 추상화하지 않음
- 근본원인 문장은 '무엇이 어떤 상태여서, 누구의 어떤 행동이 어려워지는지' 알 수 있게 씀.
  범주 이름이나 '부담·제약·어려움' 같은 말만으로 원인을 대신하지 않음
- 근거가 아직 확인되지 않은 원인도 문장의 구체성은 유지하고 '검증 전 가설'로 따로 표시함.
  불확실성을 피하려고 원인을 결과나 현상으로 바꿔 쓰지 않음
- 근거는 칸마다 '사실(출처) / 경험상 판단 / 검증 전 가설' 중 하나로 표시함
- 우리 서비스가 바꿀 수 없는 원인(외부 플랫폼 규칙, 타인이 만든 콘텐츠 등)은 근본원인으로 선정하지 않음.
  배경으로 기록하고, 우리 손이 닿는 고리에서 근본원인을 잡음. 그 원인은 위험 목록 또는 해결 단계의 제약 조건으로 넘김

#### 핵심 근본원인 식별 형식

| 원인 후보 | 현상을 설명하는 과정 | 근거와 미확인 가정 | 관련 관점 | 우리가 바꿀 수 있는가 | 선정 이유 |
|----------|------------------|------------------|----------|-------------------|----------|
| {구체적인 원인} | {원인 → 현상으로 이어지는 과정} | {사실·경험상·검증 전 가설 표시} | {여러 측면 또는 '범주 밖'} | {예/일부/아니오} | {선정 또는 제외 이유} |

- 선정할 때는 현상과의 인과 연결, 근거의 두께, 추가로 필요한 가정, 우리가 바꿀 수 있는가를 비교함
- 관련 관점에는 여러 측면을 적거나 '범주 밖'을 적을 수 있음

### 2. 문제가설 검증

#### 문제검증 인터뷰
- 대상자별 문제검증인터뷰 결과를 개별적으로 생략하지 않고 모두 제공
- 각 개별 인터뷰 결과에 문제 가설 3개의 중요도와 불편도를 5점 만점으로 평가한 결과 포함
- 각 문제의 근본원인에 대한 동의 여부도 조사

**인터뷰 결과 형식:**
```markdown
## 인터뷰 결과지 N
**인터뷰 일시:** {날짜}
**장소:** {장소}

### 인터뷰 대상
- **이름:** {이름}
- **성별:** {성별}
- **연령대:** {연령대}
- **직업:** {직업}

### 문제 검증
**문제 1: {문제}**
- 중요도: {점수}/5
- 불편함 정도: {점수}/5
- 근본원인에 대한 동의여부: {의견}

### 고객 관점 문제
{고객이 제시한 더 중요한 문제}

### 개선 제안
{고객의 개선 아이디어}
```

#### 문제검증 인터뷰 결과 취합 형식
```markdown
## 문제별 중요도/불편도 평가
| 항목 | 문제1 중요도 | 문제1 불편도 | 문제2 중요도 | 문제2 불편도 | 문제3 중요도 | 문제3 불편도 |
|------|------------|------------|------------|------------|------------|------------|
| 평균 | {점수} | {점수} | {점수} | {점수} | {점수} | {점수} |
```

### 3. 비즈니스 가치 도출

근본원인을 제거하여 문제를 해결했을 때 고객과 회사가 얻게 되는 비즈니스 가치를 각각 3개 이하로 도출함.

```markdown
## 고객측면의 비즈니스 가치
- {비즈니스 가치 1}
- {비즈니스 가치 2}
- {비즈니스 가치 3}

## 회사측면의 비즈니스 가치
- {비즈니스 가치 1}
- {비즈니스 가치 2}
- {비즈니스 가치 3}
```

## 품질 기준

### 완료 체크리스트
- [ ] 핵심 문제 3개 도출
- [ ] 각 문제별 5WHY 완성 (최소 5단계)
- [ ] 4가지 측면(심리적/제도/맥락적/커뮤니케이션)을 출발점으로 원인 후보를 살펴보고, 구체적인 원인을 선정
- [ ] 근본원인이 우리 서비스가 바꿀 수 있는 원인인지 확인
- [ ] 근거마다 사실·경험상 판단·검증 전 가설 표시
- [ ] 문제검증 인터뷰 결과 개별 제공 (종합 요약만 하지 않음)
- [ ] 비즈니스 가치 도출 (고객/회사 각 3개 이하)
- [ ] 유저저니맵의 Pain Points와 연결 확인
- [ ] 문제는 고객 관점에서 작성, 솔루션 미포함

### 정량 기준
- 핵심 문제: 3개
- 5WHY: 문제당 5단계
- 근본원인 검토: 4가지 측면
- 문제검증 인터뷰: 사용자 입력 수만큼 (기본 10명)
- 비즈니스 가치: 고객/회사 각 3개 이하

## 주의사항

- 문제는 고객 관점에서 작성
- 솔루션은 포함하지 않음
- 5WHY는 최소 3단계 이상
- 인터뷰 결과를 종합 요약만 하지 않을 것
- 모든 대상자의 인터뷰 결과 개별 제공
